# SYS-07 界面、存档、无障碍与质量保障

## 1. 系统目标

保证八组业务系统在手机和桌面上始终可理解、可操作、可恢复。界面只呈现江湖中的处境、条件和结果；存档必须承受长期内容扩展；测试必须在发布前发现坏跳转、重复奖励和手机布局回归。

## 2. 当前基础与缺口

已有：

- 原生HTML、CSS和ES Modules；
- 单一事件委托与稳定`data-action`；
- 数字键一至九；
- 原生按钮、输入框和键盘焦点；
- 390×844与桌面响应式；
- 844×390手机横屏双栏；
- 四处2D场景、可查看物件、人物站位和折叠行路图；
- 场景在左、叙事行动在右的集中布局，以及人物／行囊／武学三个边缘抽屉；
- 可回看的右侧叙事卷轴，统一保存旁白、人物对话、玩家选择与当前行动；
- 行动内嵌条件摘要、可展开判定详情，以及普通／重要／危险／不可用四种文字语义；
- `escapeHtml()`；
- 本地存档版本5以及版本2／3／4迁移；
- CDP完整浏览器流程。
- 入口样式、主模块及其依赖使用同一发布版本参数，阻止GitHub Pages与手机浏览器缓存混用新旧文件；
- 主模块超过三点五秒仍未渲染时显示世界内恢复入口，玩家可以强制取回最新资源而不是停留在白屏。

缺口：

- 后续系统信息密度会远高于首章；
- 单存档无法支持坏档恢复和路线试验；
- 存档字段增长缺少统一迁移表；
- 自动流程只覆盖主要成功路线；
- 条件、伤势、证据、关系和日程缺少统一组件；
- 没有减少动态效果、高对比和屏幕阅读器检查；
- 内容错误不能在发布前统一阻止。

## 3. 信息架构

一个标准场景按以下顺序呈现：

1. 地点、时段和当前身份；
2. 2D场景、可查看物件和在场人物；
3. 眼前发生的事情；
4. 最危险或最紧迫的变化；
5. 条件、伤势、关系或证据板；
6. 可执行行动；
7. 上一步结果和资源变化；
8. 可折叠的行路图、人物卡、物品、武学、日程和记录。

手机端不得让状态栏先占满首屏。玩家进入页面后应先看见困境和至少一个行动。

桌面与横屏的信息空间固定为两块：场景区只负责地点、人物、热点和当前所见；叙事区以连续卷轴呈现此前旁白、人物对话、玩家选择、当前文字、条件反馈和行动。横屏以1672×941为视觉坐标系等比缩放，场景与叙事宽度约为2:1，超宽或非16:9设备使用留黑而不是分别压缩文字、按钮与间距。点击场景热点时，原地热点切换为琥珀色双环，由细线连接场景内的半透明“所见”卡；卡片只说明当前发现和察觉依据，不推进右侧剧情，再次点击同一热点收起，点击其他热点直接替换内容。新场景渲染后自动滚到“眼下”，但不删除此前经过。人物、行囊与武学放入三个独立边缘抽屉，不再作为常驻第三、第四块阅读区域；此前经过直接留在叙事卷轴，不另设重复入口。

### 4.1 章末江湖留痕

M4开始在篇章收势生成五至八句“江湖留痕”，用于回答玩家做了什么、失去了什么、谁记住了这件事、下一步还能依靠谁。它不是开发总结，也不显示未见路线。

规则：

- 每句话都引用一个已发生事件、人物记忆、关系／身份变化、物品来源或地点状态；
- 点击可展开世界内依据，例如“沈福已失踪；沈家侧门无人再为你开门”；
- 同一事实只生成一次，不用形容词堆叠虚假成就；
- 至少包含一项玩家主动选择和一项永久代价；
- 只汇总业务状态，不在界面层创造新的剧情事实。

### 4.2 已掌握流程的快结算

安全、重复且不存在新判断的日常差事或旅行可以合并为一次结果。只要存在限时窗口、人物请求、关系选择、追踪风险、新能力首次兑现或资源不足，就必须恢复完整交互，不能用快结算跳过有意义的选择。

## 5. 玩家可见文本规则

- 只出现世界、人物卡、场景、事件、条件、结果和可操作反馈；
- 不出现Demo、原型、测试、构筑、存档版本、事件ID和成功率；
- 不出现现实、论坛、武道局、其他玩家；
- 新名词首次由人物、场景或物品解释；
- 禁用行动说明世界内缺口；
- 条件信息直接随选项显示，点击可展开完整说明；
- 普通、重要、危险、不可用分别使用青、金、赤、灰，并同时显示文字状态；
- 成人情节只保留动机与压力；
- 动态姓名、物品和自定义文本经过`escapeHtml()`；
- 调试信息只在开发检查中生成，不渲染给玩家。

## 6. 存档版本5

规则化夜战与回报秘密链落地时把存档升至版本5。当前仍保留顶层兼容字段，并在`p0`嵌套状态中增加当前武学、带检定明细的战斗履历、死劫履历和夜袭计划；顶层`fateSeed`固定同一旅程的因果骰，`narrativeLog`最多保留二十四条已发生场景与玩家选择。旧存档缺失种子时根据原有角色与首条事件生成稳定兼容种子，不能因刷新页面改变骰点：

```js
{
  version: 5,
  fateSeed: "一条旅程固定使用的因果种子",
  meta: { createdAt, updatedAt, playTime, routeName },
  character: {/* 属性、境界、武学 */},
  inventory: {/* 物品、银钱 */},
  story: {/* 场景、事件、事实、检查点 */},
  world: {/* 日期、地点、地点状态 */},
  relationships: {/* NPC和势力 */},
  conditions: {/* 伤势、毒、心神 */},
  narrativeLog: [{ id, context, title, lines, choice, choiceSource, choiceKind }],
  p0: {
    battleHistory: [{ battleId, round, action, intent, result, rating, check }],
    battleOutcomeGrade,
    battleEdge
  },
  preferences: {/* 字号、动态效果 */}
}
```

不把渲染后的HTML、函数、Map、Set、Date对象或循环引用写入存档。

## 7. 迁移策略

- 每个版本只负责从前一版本迁移；
- 版本2／3继续先补齐P0默认状态，版本4再补齐`activeMartial`、`battleHistory`、`deathRecords`与`assailantPlot`；
- 迁移前先校验基本类型；
- 缺失字段取`createInitialState()`默认值；
- 未识别字段不直接删除，先写入迁移报告；
- 迁移失败保留原始存档并提供重新开始，不覆盖坏档；
- 迁移函数必须可重复执行而不重复奖励。

版本3关键迁移：

- 五维、五禽和宝鱼属性进入`character`；
- 现有武学、医术、炼丹进入统一能力结构；
- 六枚回春丹、银柳木竿、血书、玉佩和银钱进入库存；
- 龙青鱼、曹青、王五、沈福进入关系结构；
- 当前场景和已完成奇遇进入事件状态；
- 命灯检查点迁入`story.checkpoints`。

版本4关键迁移：

- 已有武学不重复发放，缺失的当前运用位置取空值；
- 字符串死因记忆转换为兼容死劫履历；
- 夜袭回报条件链从`unknown`开始，不倒推发放鱼鳞铜签；
- 既有战斗、伤势、桩功、关系和终章结果保持不变。

## 8. 存档槽与恢复

P0继续保留一个自动进度，但增加：

- 写入前内存校验；
- 上一次成功存档备份；
- 读取失败回退备份；
- 显示世界内的“续行”入口，不显示自动保存术语。

P3再增加三个手动旅程槽和关键节点复制，不允许在战斗结算中任意读档绕过命灯。

## 9. 无障碍与手机要求

- 390×844无横向滚动；
- 390×844战斗页的敌方单位栏、战场热点和身位图互不遮挡，阶段条与三项推荐行动在预留手机浏览器底栏后仍完整可见；
- 1672×941标尺下顶栏、2:1分栏、开局三个行动和三个羊皮纸入口的相对尺寸符合确认效果图；
- 844×390横屏无横向滚动，等比缩放后的场景与叙事必须同时在首屏出现；
- 横屏叙事栏可独立滚动，不能拖走左侧场景；
- 叙事栏默认定位当前场景，向上滚动可回看先前旁白、对话和玩家选择；
- 不可用选项保留可读灰色文字，并可展开查看为什么无法执行；
- 最小触控目标44×44；
- 场景热点具备文本标签、键盘焦点和点击后的文字说明；横屏展开卡必须留在场景边界内，不遮挡主角、关键热点和三个边缘入口，连线随画布缩放重算；
- 正文、条件和行动保持足够对比；
- 不只用颜色区分满足、危险和锁定；
- 焦点顺序跟随视觉顺序；
- 场景切换后焦点回到新场景标题；
- 数字键不抢占输入框；
- 支持浏览器放大至200%；
- 尊重`prefers-reduced-motion`；
- 图标有文本标签；
- 战斗和倒计时不要求快速反应。

## 10. 测试层级

### 纯规则测试

覆盖条件、效果、战斗、伤势、配方、关系、时间、调查和迁移。

### 内容校验

由SYS-08检查节点引用、奖励幂等、首次解释、禁用术语和能力兑现节点。

### 浏览器主路线

每个里程碑至少一条完整成功路线。

### 浏览器风险路线

至少覆盖：

- 一次死亡回照；
- 一次非致命失败；
- 一次完整的“我方消耗气机—提前或自动收势—三名敌人依序行动—下一轮恢复气机”；
- 一次换位改变距离、一次遮挡降低远程伤害，以及一次封锁矮墙改变脱身条件；
- 同一夜战节点读取两次仍得到相同骰点；
- 大成、带伤与失手结果都进入叙事、存档和后续状态；
- 一次错过窗口；
- 一次关系破裂；
- 一次联系人失踪、死亡或被替代后旧入口关闭；
- 一次M4章末江湖留痕，并逐句核对来源状态；
- 一次已掌握安全差事快结算和一次因突发窗口被迫展开完整流程；
- 一次炼丹失败；
- 一次旧存档恢复；
- 一次手机完整操作。

### 布局检查

1280×720、390×844、844×390、200%缩放，无横向溢出和关键按钮截断；战斗页额外检查单位栏与场景分区、环境热点与身位节点互不覆盖、阶段和气机始终可见，以及三项推荐行动在首屏安全区内完整出现。

浏览器主路线同时记录场景ID、热点数量、人物揭示名称、路线节点数量、随身册数量、叙事记录数量、条件详情数量、右栏横向溢出和场景／叙事是否按方向正确分栏，防止视觉层存在但没有跟随剧情切换。

## 12. 发布检查

每次修改完成后：

1. 运行规则测试；
2. 运行内容校验；
3. 运行受影响浏览器路线；
4. 检查桌面和手机；
5. 确认运行异常为空；
6. 清理配置、日志和截图；
7. 更新README、设计和系统文档；
8. 提交并推送GitHub；
9. 确认线上地址返回成功且包含新内容。
10. 确认`index.html`中的样式和主模块版本与主模块、规则模块的依赖版本一致。

## 14. 完成标准

当前纵切完成要求版本2／3／4存档可以无损迁移到版本5；旁白、对话、玩家选择和因果骰结果可以在右侧叙事卷轴回看；条件化选项能直接显示并展开判定信息；同一因果节点不能靠读取进度改变骰点；规则化夜战、失败推进、回报秘密链、死亡回照和终章恢复在桌面与手机通过；业务规则无需读取DOM；玩家界面没有内部字段、旧剧情或产品术语。P1-A还要求M4三条长期路线、联系人断线、失败回流、快结算和章末江湖留痕均能在桌面、竖屏与横屏恢复，且每条留痕可追溯真实状态。
