# SYS-01 叙事事件与奇遇条件系统

## 1. 系统目标

把当前“一个场景对应一个renderer和handler”的剧情特例，升级为能够承载九十八章后续内容的通用事件系统。

系统必须让玩家通过行动看见因果：先观察事件，再发现条件，选择目标结果，支付资源或风险，最后改变人物、物品、地点和未来入口。

## 2. 当前基础与主要缺口

当前已经有：

- 稳定的场景状态机；
- 固定`data-action`事件委托；
- 破庙、龙青鱼、曹青和王五的条件选择；
- 部分死亡回照和提前收束；
- 一次性奖励保护。
- 夜战、雨中追查和回报反制共用的“动作＋对象”定义；
- 一条由战斗结果决定入口、由四项条件开放高阶结果的秘密链；
- 第三十至五十四章三个篇章、二十六个内容节点和自动引用校验。

当前缺口：

- 条件、消耗、奖励和跳转散落在渲染与handler中；
- 布尔字段过多，无法表达事件已见、已知、进行中、过期或部分解决；
- 旧章事件仍难以自然支持多个目标结果，新夜袭链已完成首个数据化样板；
- 隐藏条件与已知条件没有统一信息层级；
- 线索、推测、确证和错误判断没有系统状态；
- 回照点依赖手工复制状态，后续容易漏字段；
- 内容节点能跳转，但还没有统一表达人物欲望、解法覆盖、失败推进、共同回流和下场回响；
- 人物见证、权限断开和长期门路变化尚不能由事件定义直接校验。

## 3. P0范围

P0必须支持第三十至五十四章：

- 三夫人病危的多阶段诊断与救治；
- 紫龙换血丹的条件和代价；
- 春风化雨针取得后的救人／杀人分支；
- 杀死、制伏和脱身产生不同追查入口，并允许反用夜袭回报渠道；
- 第一次战斗失败回照；
- 拜师与桩功二选一；
- 八月十五重返破庙；
- 灵猴关系、猴儿酒分配和隐藏区域。

P0不做随机生成事件、无限委托或大规模开放世界。

## 4. 事件数据模型

建议新增内容节点结构：

```js
{
  id: "shen_third_lady_diagnosis",
  arc: "third_lady",
  kind: "scene",
  title: "帘后问脉",
  location: "shen_inner_house",
  availability: [/* 条件 */],
  reveal: [/* 信息揭示规则 */],
  actions: [/* 行动 */],
  checkpoint: "third_lady_entry",
  onEnter: [/* 一次性效果 */],
  onExpire: [/* 错过效果 */]
}
```

每个行动至少包含：

```js
{
  id: "inspect_meridians",
  label: "沿腕脉查气血",
  requires: [/* 可见或隐藏条件 */],
  costs: [/* 时间、体力、物品、关系 */],
  check: {/* 属性、技能、难度和环境修正 */},
  outcomes: [/* 成功、部分成功、失败、致命失败 */],
  once: true
}
```

所有内容对象必须保持JSON可序列化，不保存函数和DOM引用。

### 4.1 局面盒与解法矩阵

从第五十五章起，核心内容不再先写线性任务链，而先定义一个“江湖局面”：

```js
{
  id: "shen_fu_dirty_money",
  stableFacts: [/* 不随路线改变的事实 */],
  actors: [{ npcId, wants, fears, bottomLines, knownFacts }],
  playerQuestion: "曹青不在以后，这笔钱和沈福该怎么处理？",
  approaches: [/* 上交、分赃、藏匿、设局、拒收等过程 */],
  solutionMatrix: [/* 条件、代价、失败推进、长期后果 */],
  convergence: [/* 各路线可以自然回流的共同节点 */],
  echoes: [/* 下一场景承认旧状态的短回声 */]
}
```

设计约束：

- 每个核心局面至少有三条可行过程，其中至少两条不以正面战斗为中心；
- 每个事件最多制作三种核心内容变体，其余状态用一至三句短回声承认，避免条件组合爆炸；
- 汇合只合并舞台，不抹掉伤势、债务、证据、身份、地点状态和人物记忆；
- 安全退出、错过、失败推进、带价成功和死亡分别定义，不能统一写成“失败”；
- 解法矩阵先于场景正文与战斗配置完成，不能写到某个选项时才临时决定后果。

## 5. 通用条件

条件类型至少包括：

| 类型 | 示例 |
| --- | --- |
| 属性 | 有效悟性达到五 |
| 能力 | 医术二级、鱼跃龙门诀 |
| 物品 | 持有紫龙换血丹或银针 |
| 人物关系 | 白栀云信任达到二十 |
| 身份权限 | 获准进入沈家内宅 |
| 时间 | 八月十五辰时前 |
| 地点 | 身在破庙后山入口 |
| 事件阶段 | 已诊断但尚未用药 |
| 情报 | 已确证走火入魔而非中毒 |
| 身体状态 | 自身未重伤、病人仍有一刻钟 |
| 世界状态 | 金陵戒严、毒蛇帮警戒升高 |

条件返回统一结果：`met`、`visible`、`reason`和`progress`。界面只显示世界内理由。

## 6. 事件生命周期

每个事件采用统一状态：

```text
unseen → discovered → active → resolved
                     ↘ failed
                     ↘ missed
                     ↘ expired
```

- `unseen`：玩家不知道事件存在；
- `discovered`：知道事件或条件，但尚未正式介入；
- `active`：已支付进入成本或触发倒计时；
- `resolved`：完成某种结果，不等于最好结果；
- `failed`：尝试失败，可能允许回照或留下后果；
- `missed`：主动放弃或安全退出；
- `expired`：时间窗口关闭。

事件状态必须记录`outcomeId`，避免“完成”掩盖具体后果。

## 7. 信息层级与条件板

每个核心事件提供三级信息：

1. 陌生：只显示场景自然可见内容；
2. 亲历：显示已见结果、失败原因和明显缺口；
3. 看破：显示关键条件、代价、世界偏转和一项仍隐藏的高阶结果。

情报分为：

- 见闻：玩家亲眼看到；
- 推测：由见闻生成，可正确也可错误；
- 确证：通过医术、证人、物证或重复验证确认；
- 过期：世界状态变化后不再可靠。

信息默认保留，不与潜能、物品或武学争夺奖励名额。

## 8. 统一效果

事件不得直接任意改写状态。所有结果通过效果列表应用：

- `addItem`、`removeItem`；
- `changeResource`；
- `changeRelation`；
- `setFlag`、`advanceEvent`；
- `learnFact`、`confirmEvidence`；
- `addStatus`、`healStatus`；
- `learnSkill`、`advanceMastery`；
- `changeFaction`；
- `advanceTime`、`moveTo`；
- `setCheckpoint`。

效果应用必须返回变更摘要，供界面显示和测试断言。

## 9. 检定与结果深度

玩家先选行动意图，检定只决定这件事完成得多好、付出什么代价。固定因果骰不得替玩家决定是否杀人、是否背叛、是否接受感情，也不得否定已由充分证据确认的常识动作。

检定不只返回成功／失败。统一使用：

- 完全成功；
- 部分成功；
- 带代价成功；
- 普通失败；
- 致命失败。

同一行动应因能力走得更深。例如诊脉：

- 无医术：只能看出呼吸紊乱；
- 医术一级：排除外伤；
- 医术二级：区分走火与中毒；
- 医术二级＋春风化雨针：看见阻塞穴位；
- 再有白栀云信任：获准检查练功秘籍和旧伤。

## 10. 回照与幂等

- 检查点保存完整业务状态快照，不包含DOM和临时显示状态；
- 每次奖励带唯一`effectId`，已经应用的效果不得重复；
- 回照恢复到快照后，保留玩家记忆日志和已经亲历的死因；
- 非致命失败可以只回到事件阶段，不熄灭命灯；
- 致命失败由SYS-03决定是否消耗命灯；
- 事件过期不能通过刷新页面恢复。

## 11. 建议纯规则接口

```js
getEventState(eventId, state)
discoverEvent(eventId, state)
getAvailableActions(eventId, state)
evaluateConditions(conditions, state)
resolveEventAction(eventId, actionId, state)
applyEffects(effects, state)
buildConditionBoard(eventId, state)
createCheckpoint(checkpointId, state)
restoreCheckpoint(checkpointId, state)
validateEventDefinition(event)
```

## 12. UI要求

- 场景正文只写人物、环境和眼前变化；
- 条件板显示已满足、未满足、未知代价和限时；
- 禁用行动仍可查看世界内原因；
- 结果页明确列出时间、物品、伤势、关系和新入口变化；
- 不显示事件ID、检定公式、版本或“成功率”；
- 手机端先显示当前困境，再显示条件和行动。

## 13. 测试矩阵

P0至少覆盖：

- 未发现事件时不泄露三夫人身份和病因；
- 同一诊断行动因医术不同产生三种深度；
- 重复进入不重复扣药材或增加好感；
- 主动放弃留下`missed`而非`resolved`；
- 八月十五过期后事件进入`expired`；
- 死亡回照保留死因见闻但恢复资源；
- 版本3存档迁移后现有首章事件仍是正确状态；
- 每个节点引用的下一节点存在。
- M4局面至少三条过程可达，其中至少两条非战斗；
- 普通失败会推进警觉、债务、假情报或失去时机，而不是只返回同一选项；
- NPC只对亲见、被告知或可靠传播的行为作出反应；
- 汇合后仍保留沈福结局、沈家身份、联系人和不义之财来源；
- 核心内容变体不超过三种，其他有效状态在下一场景至少获得一次回声。

## 14. 完成标准

P0完成标准仍是“三夫人病危”完整流程不需要新增专用状态转移函数、所有条件和效果可以被纯规则测试、旧首章不回归。P1-A完成还要求“沈福反目”通过同一事件结构表达局面盒、至少三条长期结果、失败推进、人物见证、门路断开与下一场景回响，而不是为每条路线继续增加专用handler。
