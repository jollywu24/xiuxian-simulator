# 旧版叙事 RPG 研发约束

维护旧版的对应系统时读取相关章节；不要求每项任务通读全文。本文承接从 AGENTS.md 移出的旧版规则，不是新沙盒的产品规格。沙盒按 [定稿入口](sandbox/README.md) 执行；实际行为以入口代码和测试为准，任务范围与授权遵守根目录 [AGENTS.md](../AGENTS.md)。本文及代码路径均以仓库根目录为基准，具体系统公式和设计状态仍由系统文档维护。

## 1. 产品与术语

- 文字、人物关系与状态系统是玩法核心；
- 2D 场景、热点和路线可视化负责建立空间感；
- 当前发布形态是原生浏览器游戏；MVP只保证桌面与手机横屏可玩，手机竖屏只显示横置提示；
- 长期目标包含桌面封装与 Steam，但不能为尚未接入的平台破坏网页版本。

世界只发生在“大曜”高武江湖。玩家从低位人物开始，通过观察、选择、关系、武学、物品和战斗逐步取得行动权。

核心循环：

> 看见眼前局面 → 选择行动意图 → 由属性、武学、装备、关系、见闻与固定因果共同决定完成质量 → 承担真实后果 → 用新能力或新门路打开下一段局面。

产品判断顺序：

1. 玩家是否先看懂自己是谁、身在何处、眼前有什么麻烦；
2. 选择是否改变资源、关系、权限、地点或后续行动；
3. 失败是否带来新局面，而不是只让玩家重复读档；
4. 新武学、物品、见闻或关系是否在一至两个场景内得到亲手兑现；
5. 系统复杂度是否通过场景与反馈被玩家自然理解。

当前稳定名词：

- 默认主角：陈司命，十六岁；
- 武境：未入门、锻体、聚气、通脉、宗师；
- 武学大类：心法、招式、轻功、锻体；
- 招式子类：剑法、刀法、拳掌、枪棍、暗器；
- 武学品阶：粗浅、寻常、上乘、绝学、镇派；
- 战斗用语：伤害、防御、减伤、远程；不要重新使用“攻势、防守、护身、远手”等旧称；
- 玩家可见的三种目标出身：世家旁支、市井子弟、身世成谜。

目标设计与已发布实现必须分开陈述。出身系统的现行规格见 `docs/systems/11_ORIGIN_PROLOGUES.md`，实际可玩状态以 `web/origin-core.mjs`、`web/wudao-app.mjs` 和测试为准，不得把设计文档中的待制作内容描述为已经上线。

## 2. 玩家可见文本

所有玩家文本必须属于故事世界、人物、场景、事件、条件、结果或可执行反馈。

禁止出现在游戏中的产品语言包括但不限于：

- Demo、P0/P1/P2、原型、测试、构筑、开发进度；
- 车卡、自动存档、状态键、内容节点、流程回流；
- 现实世界、论坛、武道局、其他玩家。

写作方法统一采用“具体经历式描述”：

> 生活环境或眼前所见 → 做过或正在发生的具体事情 → 因此知道或能够做到什么。

执行标准：

- 用动作、物件、地点和生活细节证明能力，不用抽象标签替角色下结论；
- 出身只交代经历、见识、权限和代价，不替玩家决定善恶与性格；
- 避免对仗口号、抽象概念堆叠、连续四字短语和刻意的“不是……而是……”；
- 替换姓名后仍适用于任何武侠角色的句子，必须改得更具体；
- 旁白可以有武侠小说或说书人的节奏，但首先要清楚、自然、可行动；
- 详细方法、反例和检查表见 `docs/systems/08_CONTENT_PIPELINE.md`。

信息揭示必须遵守人物认知：

- 未见过的人物不提前显示姓名、身份或关系；
- 未查明的地点、势力、物品来历和幕后动机不提前剧透；
- 新名词第一次出现时由场景、人物或物品自然解释；
- 青衣妇人首次出现时不提前显示龙青鱼、漕帮帮主夫人或陆连山；
- 出身选择阶段使用“世家旁支”，正式进入相关剧情前不显示“沈家”；
- 出身选择界面不展示主角立绘、世界观长文、初始物品清单、未来任务或隐藏风声。

选择与反馈：

- 选项直接标明有关的属性、武学、装备、关系、见闻、资源或兵器条件；
- 条件详情可以展开查看依据；
- 不可用选项保留并置灰，明确说明缺少什么；
- 重要、危险和不可用状态不能只靠颜色，必须同时有文字或图形标识；
- 玩家选择落定后写入右侧叙事信息流，结果紧随其后，旧记录自然上推；
- 动态姓名和其他外部输入必须经过 `escapeHtml()`。

## 3. 系统设计原则

### 3.1 局面与选择

- 用“稳定事实、人物欲望、可用手段、代价、失败推进、共同回流”组织局面；
- 玩家决定行动意图，固定因果骰只决定完成质量，不替玩家决定立场；
- 同一状态与同一行动必须得到同一因果结果，禁止通过读档刷新点数；
- 普通失败继续推进并留下代价；只有明确死局或累积到致命后果时才进入死亡；
- 核心选择必须在下一场景产生人物、地点、权限、资源或风险上的可见回响；
- 关系不是单纯好感条，还应改变透露、传授、引见、包庇、牺牲和求助权限；
- 身份使用离散社会位置，不做另一条经验条；
- 世界只模拟能形成选择的部分，不为完整感提前建设全 NPC 日程、随机物价或通用天气。

### 3.2 成长、武学与装备

- 阅历是玩家可见的武学研习资源；内部旧字段 `potential` 只作为兼容镜像，不在新界面继续扩散；
- 已学武学与当前携带武学分开；战斗只读取携带内容；
- 真气在聚气后才可用，未入门和锻体阶段不伪造真气数值；
- 真气催动强化原动作，沿用同一判定，不复制一套“强化技能”按钮；
- 装备、人物属性、境界、武学和伤势必须接入同一战斗公式；
- 不建立与现有引擎并行的第二套战斗公式；
- 装备首版不做耐久、随机词缀、强化、套装和繁复部位扩张；
- 新能力至少在战斗、调查、旅行、关系或制度行动中的两类场景产生用途。

### 3.3 状态与存档

- `createInitialState()` 是运行状态默认值的事实来源；
- 状态只保存 JSON 可序列化值；
- 带奖励的效果必须有稳定 ID、保持幂等，handler 必须防止重复领取；
- 内容字段变化时先设计迁移，再提升状态版本；
- 不改变现有存档主键，不用新空档覆盖旧档或损坏档；
- 浏览器主档、校验、备份与桌面原子文件规则见 `docs/SAVE_ARCHITECTURE.md`；
- 修改人物、装备、武学、战斗或剧情状态后，必须检查旧版本迁移。

## 4. 技术架构

旧版网页使用原生 HTML、CSS 和 ES Modules，已有 Three.js 世界；这不是新沙盒必须采用 3D 的要求。维护旧版时，Three.js 运行时与 MIT 许可证固定分发于 `web/vendor/three/`，叙事、存档和战斗仍由原纯规则模块负责，空间表现不得另建游戏规则。代码导航与入口统一见 `PROJECT_CONTEXT.md`，打包和发布行为以实际脚本及 `docs/RELEASE.md` 为准。

Spine 官方运行时进入发布目录、提交或 Pages 前，须有适用的 Professional／Enterprise 许可及同版本编辑器导出验证。已有可核验记录时复用证据；缺少时只阻塞 Spine 分发与对应验收，可继续静态回退及其他独立工作。程序化 3D 角色不依赖 Spine。

`web/app.mjs`、`web/game-core.mjs` 和 `tests/core.test.mjs` 是旧版迁移参考，正式入口不加载。除非用户明确要求清理，不要顺手重构、删除或继续在其中开发。

架构约定：

- 纯规则模块不得访问 DOM、`localStorage` 或网络；
- 规则返回值保持可序列化，并优先由测试直接验证；
- 页面交互继续使用统一事件委托和稳定 `data-action`、`data-value`；
- 新场景必须同步渲染映射、handler、视觉模式、默认状态、必要的场景物件／路线、测试和文档；
- 内部英文状态键不得直接进入玩家界面；
- 修改运行时代码后，检查 `web/index.html` 及模块 import 的发布版本参数，统一递增，避免手机缓存混用新旧模块；
- 主模块启动失败时必须保留可见的恢复入口，不能只显示空白页。

- `?debug=1` 的 `window.WudaoDebug` 只服务自动回归，普通入口不得注入调试对象或显示调试控件。
- 新增内容节点和效果使用稳定 ID，选择结果必须落入状态，不能只换文案。
- 不为局部需求额外引入前端构建器、资产 CDN 或通用资产管理器。

## 5. 界面与美术

- 桌面与手机横屏以“左侧场景、右侧叙事信息流”为主要布局，基础宽度约为2:1，不改成75:25；
- 左侧只呈现场景对象、选中反馈、环境变化和空间出口；完整对象描述、条件与行动统一进入右侧当前上下文；
- 右侧由可回看的历史卷轴和可替换的当前上下文组成；浅观察只替换当前上下文，不写入历史，正式行动、对白和局面变化才追加历史记录；
- 到达场景属于已经发生的叙事，首次进入必须以具体现场旁白写入历史；当前上下文为空时不得用任务标题、计数卡、系统教学或操作说明冒充叙事信息流；
- 手机竖屏不渲染可玩界面，只显示世界内的横置提示；旋转到横屏后恢复当前流程；
- 人物、行囊、武学是三个同级入口，打开后覆盖完整设备视口；
- 人物页不显示命灯、阅历或装备耐久；显示境界、气血、真气、防御、减伤、特性名称和装备；
- 装备点击后先打开详情，再由详情中的装备、替换或卸下按钮确认；
- 行囊和装备的名称、品质文字与品质底框使用同一品质色；
- 武学空位、图标和装备格保持一致的视觉尺寸，不以拉伸素材填满格位；
- 场景热点必须对应原图物件，点击同一热点、场景空白处或按`Escape`关闭右侧“所见”上下文；
- 火势、饥饿等短时变化使用场景中央飘字，最终状态留在固定区域；
- 原生按钮和输入框保留键盘焦点，数字键 `1`～`9` 继续触发当前可用行动；
- 视觉层级、最新确认效果和详细响应式标准见 `docs/systems/07_INTERFACE_SAVE_QA.md` 及用户最近确认的效果图；
- Spine 编辑器、导出数据和官方运行时必须锁定同一主次版本；未在编辑器和官方运行时中实际打开的数据只能称为“可导入预制”，不能称为已完成 Spine 工程；正式动态加载失败或设备要求减少动态时必须回退到现有静态 WebP。
- 确认效果图必须按`docs/VISUAL_IMPLEMENTATION.md`执行：冻结唯一参考和页面状态、量取尺寸、先过灰盒、按槽位生产资源、生成确定性截图、叠图比较，再把关键几何关系写入浏览器回归；不得从目测和末尾CSS补丁重新开始。

### 5.1 视口检查

涉及游戏界面或运行美术时，最低检查视口：

- `1280×720` 桌面；
- `844×390` 手机横屏；
- `390×844` 只检查横置提示、正式界面不可误触和旋转恢复；
- 涉及已确认横板效果时，再检查设计标尺视口。

任何视口都不允许横向溢出，也不以固定高度截断关键文案或操作按钮。
